## generate_ai_title 报「AI 未返回有效标题，原始回复: 」的修复
- 原因：响应里 `choices[0].message.content` 为空字符串；且上一轮把 `max_tokens` 从 1000 降到 300，思考型模型（DeepSeek 思考模式等）token 被思维链吃光 → 正文为空。原代码只检查字段存在性，未处理空串/null（null 还会被 `to_string()` 变成 "null" 当标题）。
- 修复（ai.rs）：`max_tokens` 恢复 1000；新增 `extract_message_content`，兼容 `/choices/0/message/content`（String 或数组 text/content 片段）、`/choices/0/text`、`/output_text`、`/result`，并单独取 `reasoning_content`；空 content 时区分「只有 reasoning」与「完全为空」两种中文错误提示并附 800 字符响应片段；请求加 `"stream": false`；响应体写 info 日志（截断 1000）便于导出日志排查。
- 教训：思考型视觉模型必须预留足够输出预算；解析 AI 响应不能只判断字段是否存在。
- 后续（用户手动改动）：`max_tokens` 行被注释掉不再下发（部分新版模型端点仅支持 `max_completion_tokens`），现由服务端默认输出长度控制，代码内已留注释说明。

## Rust 端为 ffmpeg 调用加串行队列（防止并发生成时 ffmpeg 被频繁拉起）
- 背景：前端 AI 生成改为并行后，多个任务会同时执行 ffprobe/ffmpeg 截帧，抢占 CPU/磁盘。
- 实现（`src-tauri/src/commands/ai.rs`）：
  - 新增 `static FFMPEG_QUEUE: OnceLock<Mutex<()>>` + `fn ffmpeg_queue() -> &'static Mutex<()>`（用 `tokio::sync::Mutex`，Cargo 中 tokio 已是 features=["full"]，可用）。tokio Mutex 为 FIFO 公平锁 → 天然队列，先到先执行。
  - `generate_ai_title` 中把「probe_video_duration + extract_frame」整体放进 `let _queue_guard = ffmpeg_queue().lock().await;` 临界区，块外仍并行执行 AI 网络请求（锁只覆盖 ffmpeg 阶段）。
  - 排队可观测：记录 `queue_wait_start`，等待 ≥200ms 时 info 打印等待时长。
  - import 变更：`use std::time::{Duration, Instant}`、`use std::sync::OnceLock`、`use tokio::sync::Mutex`。
- 注意：不能在 async 中跨 await 持有 `std::sync::MutexGuard`（非 Send，Tauri command 的 Future 需 Send），必须用 tokio 的异步 Mutex。
- 格式：`src-tauri/rustfmt.toml` 为 max_width=100 且含 nightly-only 的 `imports_granularity`，stable rustfmt 会输出大量既有代码差异 → 不要整文件 `cargo fmt`，只手动按需换行。
- 验证：`cargo check` 通过。

## ffmpeg 逻辑重构到独立模块 + 截帧命令优化（用户反馈截帧要十多秒）
- 重构：新建 `src-tauri/src/utils/ffmpeg.rs`（`utils/mod.rs` 加 `pub mod ffmpeg;`），从 `commands/ai.rs` 迁出所有与 ffmpeg/ffprobe 相关的代码：`resolve_ffmpeg`、`run_process`、`probe_video_duration`、`parse_ffmpeg_duration`、`extract_frame`，以及 ffmpeg 串行队列（原 `FFMPEG_QUEUE` + `ffmpeg_queue()`，现为 `pub async fn ffmpeg_queue_lock() -> MutexGuard<'static, ()>`）。理由：ffmpeg 能力与 AI 业务无关，commands 层只应保留 AI 逻辑。
- 新增高层 API `capture_frame_near_end(ffmpeg, video_path, from_end_secs) -> Result<(String, Vec<u8>)>`：`(时间点描述, JPEG 字节)`。
- 性能优化（原流程要跑两个外部进程：ffprobe 探测时长 + ffmpeg 截帧，每个都要解析一遍大文件）：
  - 优先 `ffmpeg -y -sseof -3 -i <file> -frames:v 1 -an -sn -dn -f image2pipe -c:v mjpeg -q:v 5 pipe:1`：从末尾倒数定位，一次调用搞定，省掉时长探测。
  - 失败/空输出时回退：`probe_video_duration` + `extract_frame`（`-ss` 在 `-i` 前，输入侧快速 seek，这点原命令是对的）。
  - 两处截帧都加 `-an -sn -dn`（不要音频/字幕/数据流解码）。
  - 全链路计时日志：`run_process` 打印每个外部进程耗时与完整命令行；`capture_frame_near_end` 打印探测耗时、截帧耗时、总耗时；`generate_ai_title` 打印队列等待（≥200ms）。
- 排查指引：日志里若「外部进程耗时」本身就十多秒 → 瓶颈在 ffmpeg 解析/解码大文件（无索引容器、GOP 大、高分辨率软解）；可选加速 `-skip_frame nokey`（直接取最近关键帧，快很多但时间点可能提前一个 GOP，对结算画面通常无影响）。
- `ai.rs` 现状：imports 精简为 `std::path::Path`、`std::time::{Duration, Instant}`、`tracing::{error, info}`，调用 `resolve_ffmpeg` / `ffmpeg_queue_lock` / `capture_frame_near_end`。
- 验证：`cargo check` 通过，无 warning。

## 截帧图片压缩：减少提交给视觉模型的 token
- `src-tauri/src/utils/ffmpeg.rs` 新增常量：`MAX_FRAME_EDGE = 1280`（画面长边上限）、`MAX_FRAME_BYTES = 600KB`（体积上限）、`FRAME_QUALITY = "6"`（mjpeg q:v，原 5）。
- `scale_filter(edge)` 生成缩放表达式，**踩坑**：`scale=W:H:force_original_aspect_ratio=decrease` 实测会把小图放大（522x330 → 1280x808），不能用；改用只缩不放的写法：
  `scale=w='if(gt(iw\,ih)\,min(iw\,1280)\,-2)':h='if(gt(iw\,ih)\,-2\,min(ih\,1280))'`（`-2` 让另一边按比例取偶数，便于 420 采样）。实测 1920x1080→1280x720，522x330 保持不变。
- `optimize_frame(ffmpeg, frame)`：截帧后若 >600KB，调用 `shrink_frame`（stdin 管道二次编码，长边 1024 + q:v 8）再压一轮，日志打印压缩前后字节数；失败则回退原图。
- 新增 `run_process_with_stdin()`：stdin 写 `input` 后 `shutdown()` 再 `wait_with_output()`（用 `tokio::io::AsyncWriteExt`），同一进程内二次压缩，不再落临时文件。
- 取舍说明：JPEG 没有真正的无损压缩（转 PNG 体积反而更大），要省 token 只能降分辨率/质量；视觉模型内部同样会缩放输入，1280 长边对结算截图识别基本无损失。
- 验证：`cargo check` 通过；实机用 `ffmpeg`/`ffprobe` 验证缩放参数正确。

## 封面关键字匹配：修复「姜维/梦姜维」互相误命中（CoverUploader.vue）
- 背景：关键字表存在包含关系（如「姜维」⊂「梦姜维」）。子串匹配导致两类误配：标题含「姜维」时把文件名含「梦姜维」的封面带出（后端 `list_cover_images` 按子串扫描）；标题含「梦姜维」时同时命中「姜维」并把普通姜维封面带出。
- 修复（纯前端，Rust 后端无需改）：按「更长关键字优先（最具体优先）」双重过滤：
  - `extractIndependentCoverKeywords(title)`：标题侧剔除冗余短词——某关键字每次出现都被更长的命中词覆盖时才算冗余（精确按位置判断，标题「姜维大战梦姜维」中独立出现的「姜维」仍会保留）。
  - `primaryKeywordsInImage(name)` / `isImageMatched(name, matchedKeywords)`：图片侧取文件名中最具体关键字集合，与标题命中词取交集再返回。
- 效果：标题「梦姜维」只带梦姜维封面、标题「姜维」不带梦姜维封面；关键词可扩展，无需维护排除表。
- 验证：`npx vue-tsc --noEmit`、lint 均通过（0 错误）。
